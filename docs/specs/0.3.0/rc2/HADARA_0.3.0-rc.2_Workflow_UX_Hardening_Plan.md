# HADARA 0.3.0-rc.2 Workflow UX Hardening Design

## Status

Draft design for the post-`0.3.0-rc.1` workflow UX hardening mini-line.

This document turns the T-0302 post-publish recycle findings into a concrete capsule sequence for `0.3.0-rc.2`.

## Background

`hadara@0.3.0-rc.1` successfully proved the main installed-package lifecycle:

```text
task create -> evidence -> finish -> ready -> close -> audit
```

T-0302 post-publish recycle confirmed:

- npm registry metadata for `hadara@0.3.0-rc.1` is visible and improved;
- npx and global install smokes reach the installed CLI;
- help, lifecycle help, command registry, docs surfaces, and protocol migration work from the published package;
- ten temporary workflow capsules passed ready, close dry-run, close execute, and audit.

The remaining problems are workflow UX problems:

1. Fresh init followed by `hadara doctor --json` can fail because `.hadara/context/HADARA_CONTEXT.md` is missing.
2. Agents still tend to defer all documentation until after implementation.
3. Agents need clearer parallel-read / serialized-write rules.
4. `task finish --execute` can overwrite Task Board note/evidence cells.
5. Ready/close failures can be structurally correct but not prescriptive enough.
6. Required Reading can grow too large unless it becomes compact/current-state-first.
7. Existing projects must get the same improvements through `protocol migrate`, not only new `init`.

## Release Strategy

The next external release should be:

```text
hadara@0.3.0-rc.2
```

Do not jump directly to stable after these changes. Several items change user-facing behavior:

- fresh init scaffold behavior;
- protocol migration behavior;
- Task Board preservation in `task finish`;
- ready/close/harness JSON hints;
- required-reading JSON tiering.

Stable `0.3.0` should be considered only after the rc.2 installed-package recycle passes without blocker-level findings.

## Capsule Sequence

```text
T-0303 Fresh Init + Migration Context Scaffold and Doctor/Docs Cleanliness
T-0304 Workflow Documentation Timing and Concurrency Guidance
T-0305 Task Board Row Preservation in task finish
T-0306 Ready/Close Failure Guidance Improvement
T-0307 Required Reading Tier Guidance
T-0308 Required Reading Command Output Tiering
T-0309 Protocol Migration Atomic Execute Hardening
T-0310 0.3.0-rc.2 Readiness and Publish Preparation
T-0311 Atomic Write Path Containment Hardening
T-0312 0.3.0-rc.2 Post-Publish Installed-Package Recycle
```

# Core Design: `.hadara/context/HADARA_CONTEXT.md`

## Role

`.hadara/context/HADARA_CONTEXT.md` is the compact project-local context anchor.

It is not the full project state, release log, task history, or evidence log.

Its job is to help an operator or agent answer:

```text
What kind of HADARA project is this?
What should I read first?
Where is the current state?
What should I not read by default?
What write-boundary rules matter before I act?
```

## Source-of-Truth Boundaries

`HADARA_CONTEXT.md` must not become a competing source of truth.

Authoritative sources remain:

```text
.hadara/docs-registry.json
docs/DOC_REGISTRY.md
docs/TASK_BOARD.md
docs/AGENT_HANDOFF.md
docs/PROJECT_STATE.md
docs/TASK_WORKFLOW_COMMANDS.md
tasks/*/TASK.md
tasks/*/evidence.jsonl
```

`HADARA_CONTEXT.md` routes to these sources and provides compact operating rules.

## Commit Policy

`HADARA_CONTEXT.md` is project-scoped and intended to be committed unless a project deliberately opts out.

It is different from `.hadara/local/*`, which is local/private/disposable state.

## Security Policy

Allowed:

- project identity;
- HADARA profile;
- workflow routing;
- compact operating rules;
- non-secret project-specific notes.

Forbidden:

- credentials;
- tokens;
- private logs;
- raw model transcripts;
- private user data;
- machine-local absolute paths;
- large design documents;
- full release/task/evidence history.

## Initial Scaffold Content

```md
# HADARA_CONTEXT

## Purpose

This file is the compact project-local context anchor for HADARA sessions.

It is not the full project state, release log, task history, or evidence log.
Use it to decide what to read next.

## Project Identity

| Field | Value |
|---|---|
| Project | <project name or repository name> |
| HADARA Profile | basic / standard / governed |
| Primary Workflow | Task Capsules + Evidence + Handoff |
| Generated By | hadara init or protocol migrate |

## Read Routing

| Need | Read |
|---|---|
| Current project state | `docs/PROJECT_STATE.md` |
| Current/next agent handoff | `docs/AGENT_HANDOFF.md` |
| Task list | `docs/TASK_BOARD.md` |
| Command lifecycle | `docs/TASK_WORKFLOW_COMMANDS.md` |
| Document registry | `docs/DOC_REGISTRY.md` |
| Machine-readable docs registry | `.hadara/docs-registry.json` |

## Operating Rules

- Do not defer all documentation until after implementation.
- Keep capsule docs current as work changes.
- Parallelize read-only discovery and independent validation.
- Serialize writes to evidence, Task Capsule docs, shared state docs, before-hash executes, finish/close operations, and release/publish operations.

## Project-Specific Notes

Add short, non-secret notes only.

Do not store credentials, private logs, raw model transcripts, or large design documents here.
```

## Connectivity

```text
doctor
  -> checks .hadara/context/HADARA_CONTEXT.md

init
  -> creates .hadara/context/HADARA_CONTEXT.md

protocol migrate --target 0.3.0
  -> creates missing context for existing projects
  -> does not overwrite existing context
  -> does not touch context in task-scoped mode

docs registry
  -> registers context document

docs list
  -> shows context document

docs doctor
  -> detects missing or unregistered context state

docs required-reading
  -> exposes context as current-state/session-start entry point

AGENTS / IMPLEMENTATION_SOP
  -> point agents to context as compact first read

future session start
  -> consumes context together with project view, docs registry, and proof status
```

# T-0303 — Fresh Init + Migration Context Scaffold and Doctor/Docs Cleanliness

## Goal

Eliminate fresh-init doctor friction and connect `HADARA_CONTEXT.md` to init, protocol migration, doctor, docs list, docs doctor, and required-reading surfaces.

## Problem

Fresh `hadara init --profile basic|standard|governed` can succeed while immediate `hadara doctor --json` exits non-zero because `.hadara/context/HADARA_CONTEXT.md` is missing.

Fixing only `init` is not enough. Existing projects initialized with rc.0 or rc.1 need the same context scaffold through `protocol migrate --target 0.3.0`.

## Decisions

1. `HADARA_CONTEXT.md` is project-scoped and intended to be committed.
2. `init` must create the context file for all profiles.
3. Project-scoped `protocol migrate --target 0.3.0` must create the context file if missing.
4. Existing context must never be overwritten by migration.
5. Task-scoped migration must not create or modify project context.
6. Docs surfaces must agree that context is a registered current-state/session-start entry point.

## Scope

Implementation candidates:

```text
src/cli/init.ts
src/services/docs-registry.ts
src/services/protocol-migration.ts
tests/unit/init.test.ts
tests/unit/doctor.test.ts
tests/unit/protocol-migration.test.ts
docs/IMPLEMENTATION_SOP.md
AGENTS.md
docs/SCHEMAS.md, if schema references change
```

## Required Behavior

### Init

For each profile:

```bash
hadara init --profile basic --json
hadara init --profile standard --json
hadara init --profile governed --json
```

Expected:

```text
.hadara/context/HADARA_CONTEXT.md exists
.hadara/docs-registry.json registers .hadara/context/HADARA_CONTEXT.md
docs/DOC_REGISTRY.md includes the context document
hadara doctor --json does not fail due to project-context missing
```

### Project-Scoped Migration

```bash
hadara protocol migrate --target 0.3.0 --json
```

Expected dry-run action when context is missing:

```text
id: context-anchor
path: .hadara/context/HADARA_CONTEXT.md
status: planned
```

Execute requires reviewed `summary.beforeHash`.

If the file exists, action should be skipped:

```text
status: skipped
summary: existing context is preserved
```

### Task-Scoped Migration

```bash
hadara protocol migrate --target 0.3.0 --task T-XXXX --json
```

Expected:

```text
No project-context action.
No .hadara/context/HADARA_CONTEXT.md write.
```

## Docs Registry Entry

Suggested registry entry:

```json
{
  "path": ".hadara/context/HADARA_CONTEXT.md",
  "title": "HADARA_CONTEXT",
  "owner": "hadara-context",
  "kind": "project-context",
  "status": "canonical",
  "scope": "project",
  "profiles": ["basic", "standard", "governed", "hadara-dev"],
  "readWhen": ["session-start"],
  "requiredReading": true,
  "updateOwner": "mixed",
  "updatedByCommands": ["init", "protocol.migrate"],
  "managedSections": [],
  "closeSourceRole": "included",
  "supersedes": [],
  "notes": "Compact project-local context router. Do not store secrets or full project history."
}
```

If `DocumentKind` does not yet include `project-context`, add it or use `protocol` with explicit notes. Preferred: add `project-context`.

If `project-context` is introduced as a new `DocumentKind`, update every schema and consumer touched by docs registry, docs cleanup, docs list, docs doctor, and required-reading surfaces so existing registry consumers remain compatible.

## Acceptance Criteria

- AC-1: `hadara init --profile basic` creates `.hadara/context/HADARA_CONTEXT.md`.
- AC-2: `standard` and `governed` profiles also create it.
- AC-3: fresh init followed by `hadara doctor --json` does not fail due to missing project context.
- AC-4: project-scoped `protocol migrate --target 0.3.0` plans missing context scaffold creation.
- AC-5: migration execute creates context only when missing.
- AC-6: existing context is never overwritten.
- AC-7: task-scoped migration does not touch context.
- AC-8: `docs list --json` includes `.hadara/context/HADARA_CONTEXT.md`.
- AC-9: `docs doctor --json` either passes or reports specific context registry drift.
- AC-10: `docs required-reading --json` exposes context according to its current-state/session-start role.
- AC-11: `.gitignore` does not exclude `.hadara/context/HADARA_CONTEXT.md`.
- AC-12: docs registry schemas and consumers accept `project-context` if that document kind is introduced.

## Validation

```bash

npm run build

# built CLI smoke: run each profile in a separate clean temp project
```

# T-0304 — Workflow Documentation Timing and Concurrency Guidance

## Goal

Make documentation incremental and clarify read/write concurrency rules.

## Problem

Agents may implement first and write all documents afterward. This waterfall pattern creates close churn and stale close-source docs.

Agents also need explicit rules for what can run in parallel and what must be serialized.

## Decisions

1. Documentation is part of the work, not a post-work report.
2. Root docs and generated init scaffold docs must both be updated.
3. Read-only work may be parallelized.
4. Writes to HADARA state, evidence, capsule docs, and release surfaces must be serialized by write boundary.

## Scope

Update root docs:

```text
AGENTS.md
docs/IMPLEMENTATION_SOP.md
docs/TASK_WORKFLOW_COMMANDS.md
```

Update generated scaffold templates in:

```text
src/cli/init.ts
```

Update tests:

```text
tests/unit/init.test.ts
tests/unit/task-workflow-docs.test.ts
```

## Required Guidance

### Incremental Documentation Timing

```text
Do not defer all documentation until after implementation.

Keep capsule docs current as the work changes:
- PLAN before execution.
- DECISIONS, RISKS, and FILES during execution.
- TESTS and EVIDENCE immediately after validation.
- ACCEPTANCE and HANDOFF before finish/ready/close.
- Shared state docs before close-source hash is captured.
```

### Parallel vs Serialized

Parallelize:

```text
read-only discovery
rg / grep / git diff / file inspection
independent validation commands
package/registry metadata inspection
read-only diagnostics
draft preparation before writes
```

Serialize:

```text
same-file writes
evidence append
Task Capsule doc writes
Task Board writes
Project State writes
Agent Handoff writes
before-hash execute operations
task finish --execute
task close --execute
release artifact / publish operations
```

## Acceptance Criteria

- AC-1: root workflow docs explain incremental documentation timing.
- AC-2: generated init workflow docs include the same timing model.
- AC-3: root AGENTS/SOP explain read-only parallel / write-boundary serialized rule.
- AC-4: generated AGENTS/SOP include the same rule.
- AC-5: fresh init tests prove scaffolded docs include this guidance.
- AC-6: no CLI behavior changes.

## Validation

```bash
npm run test:focused -- tests/unit/init.test.ts tests/unit/task-workflow-docs.test.ts
npm run build
```

# T-0305 — Task Board Row Preservation in `task finish`

## Goal

Ensure `task finish --execute` does not erase human-authored Task Board notes or evidence-like cells.

## Current Risk

`task finish` currently compares the entire row to a canonical row and replaces it when different. The canonical row has an empty `Notes` cell. A human-authored note can therefore be lost.

## Cell Ownership Policy

For the canonical table:

```text
| ID | Title | Status | Capsule | Notes |
```

Ownership:

```text
ID: command-owned
Title: command-owned; synchronized from Task Capsule title
Status: command-owned
Capsule: command-owned
Notes: human/mixed-owned; preserve
Extra cells: human/mixed-owned; preserve
```

## Markdown Table Policy

Required:

- preserve `Notes`;
- preserve extra cells;
- synchronize title from Task Capsule title;
- update status to `Done`;
- update capsule path;
- sanitize generated title pipes so generated rows do not break the table;
- support escaped pipe preservation for existing cells where practical.

Best-effort:

- preserve inline-code pipes such as `` `a | b` `` if parser support is introduced.

Do not turn this capsule into a broad Markdown parser project.

## Scope

```text
src/task/task-finish.ts
tests/unit/task-finish.test.ts
docs/TASK_WORKFLOW_COMMANDS.md
src/cli/init.ts generated workflow docs, if ownership policy is scaffolded
```

## Out of Scope

```text
Task Board schema redesign
historical Task Board migration
managed section engine rewrite
new Task Board command family
```

## Acceptance Criteria

- AC-1: existing `Notes` cell survives `task finish --execute`.
- AC-2: extra cells survive `task finish --execute`.
- AC-3: `Status` updates to `Done`.
- AC-4: `Capsule` path updates if needed.
- AC-5: `Title` syncs from the Task Capsule title.
- AC-6: generated title containing raw `|` does not break the table.
- AC-7: escaped pipe and generated pipe title coverage are required.
- AC-8: inline-code pipe preservation is best-effort and not a close blocker unless parser support is introduced.

## Validation

```bash
npm run test:focused -- tests/unit/task-finish.test.ts
npm run build
```

# T-0306 — Ready/Close Failure Guidance Improvement

## Goal

Make ready/close/harness failures actionable.

A blocked report should tell the agent which file, heading, or table to repair.

## Decisions

1. Add hints as additive JSON fields only.
2. Do not rename existing issue codes.
3. Do not require full `proof explain` parity in this capsule.
4. Share the hint source where task ready and harness validation use the same checks.

## Hint Model

Preferred additive type:

```ts
interface RemediationHint {
  path: string;
  heading?: string;
  requiredChange: string;
  example?: string;
  blocking: boolean;
}
```

Example issue:

```json
{
  "code": "TASK_ACCEPTANCE_PLACEHOLDER",
  "path": "tasks/T-0001/ACCEPTANCE.md",
  "heading": "Acceptance Criteria",
  "message": "Acceptance criteria still contain placeholder content.",
  "fixHint": "Replace placeholder rows with concrete criteria and mark Status as Done when satisfied.",
  "example": "| AC-1 | ... | Done | evidence id or summary |"
}
```

## Scope

Required:

```text
task ready
harness validate
task close close-source blockers where applicable
JSON schema fixtures
tests for common failure cases
```

Optional:

```text
proof explain summary hints
```

`proof explain` is not part of T-0306 acceptance.

Before implementation, resolve the concrete test file list with repository search instead of relying on broad shell globs. The implementation capsule should run:

```bash
rg --files tests | rg 'task-ready|harness|task-close|schema'
```

Then pass the actual matching file paths to `npm run test:focused -- ...`.

## Acceptance Criteria

- AC-1: `task ready` placeholder or missing heading issue includes path, heading, and fixHint.
- AC-2: `harness validate` exposes the same hint model for shared checks.
- AC-3: `task close` close-source doc blockers include path-level fix hints where applicable.
- AC-4: schema fixtures are updated.
- AC-5: existing consumers tolerate additive fields.
- AC-6: `proof explain` parity is not required.

## Validation

```bash
rg --files tests | rg 'task-ready|harness|task-close|schema'
npm run test:focused -- <resolved task-ready/harness/task-close/schema fixture test files>
npm run build
```

# T-0307 — Required Reading Tier Guidance

## Goal

Introduce a compact/current-state-first reading model in docs and generated scaffold text.

This capsule is guidance-only.

## Problem

Required Reading can grow too large. Agents need a compact first-read model instead of being implicitly pressured to read all history every session.

## Tier Model

Use semantic tiers:

```text
current-state
task-work
conditional-reference
historical
excluded
```

Human-facing docs may call them Tier 1/2/3, but JSON should use semantic names later.

## Meaning

```text
current-state:
  compact documents to read first at session start or task resume

task-work:
  documents needed for the active Task Capsule workflow

conditional-reference:
  architecture/security/release/docs needed only for task type

historical:
  never default; read only when explicitly investigating history

excluded:
  superseded/archived/never-default
```

## Scope

```text
AGENTS.md
docs/IMPLEMENTATION_SOP.md
docs/TASK_WORKFLOW_COMMANDS.md
src/cli/init.ts generated AGENTS/SOP/workflow docs
```

This capsule should extend the T-0304 timing/concurrency guidance instead of duplicating it. When the same documents are touched, prefer compact cross-references to repeated rule blocks.

## Out of Scope

```text
docs required-reading --json output change
docs registry schema change
automatic archive/move/delete
physical split of PROJECT_STATE
```

## Acceptance Criteria

- AC-1: root docs describe the semantic tier model.
- AC-2: generated init docs include the same model.
- AC-3: `HADARA_CONTEXT.md` is identified as current-state entry point.
- AC-4: `PROJECT_STATE.md` full history is not mandatory every session.
- AC-5: historical/superseded docs are never default reading.
- AC-6: tests prove generated scaffold includes tier guidance.

## Validation

```bash
npm run test:focused -- tests/unit/init.test.ts tests/unit/task-workflow-docs.test.ts
npm run build
```

# T-0309 — Protocol Migration Atomic Execute Hardening

## Goal

Harden rc.2 adoption writes before release readiness so migration and docs cleanup execute paths do not leave partial or corrupted state.

## Scope

```text
common atomic text write helper

protocol migrate --execute prepare-all temp writes before commit
protocol migrate --execute rollback of already-renamed files on later commit failure

```

## Out of Scope

```text

post-publish installed-package recycle

```

## Acceptance Criteria

- AC-1: `protocol migrate --execute` validates all planned file hashes before writing any file.

- AC-4: `docs mark --execute` writes `.hadara/docs-registry.json` through temp+rename and reports write failures without corrupting the registry.
- AC-5: release readiness and post-publish recycle are renumbered to T-0310 and T-0312, with T-0311 reserved for follow-up atomic helper containment hardening.

Ten capsules are acceptable if the run remains manageable, but representativeness matters more than an exact count.
