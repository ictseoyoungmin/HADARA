# RFC: State-First Architecture (0.5 candidate)

- 상태: **RFC / 0.5 candidate** — 채택 여부는 0.4.1-rc.0 프로토타입 결과로 게이팅 (§9)
- 작성일: 2026-07-05
- 대체 문서: `docs/specs/0.4.0/state-first/proposal.md` (본 RFC가 리뷰 반영판으로 승계; proposal은 사건 기록·초기 진단의 출처로 존속)
- 리뷰 반영: 1차 리뷰(스코프 축소, rev CAS 반박, evidence locality, context 도구 재평가) 및 2차 리뷰(generated 블록 소유권 계약 조건) 합의 사항 전체 반영
- 관련 문서: `docs/RELEASE_0_4_1_RC0_FUNCTIONAL_DEBT.md`, `docs/specs/0.4.1/rc0-scope.md`

## 0. 한 문장 요약

> HADARA 안에 이미 존재하는 정답 패턴 — `evidence.jsonl`(canonical) + `EVIDENCE.md`(생성된 projection) — 을
> **구조화 가능한 상태 영역에 한해** 일반화한다. 전면 projection화가 아니다.

proposal.md의 원안("모든 마크다운을 projection으로")에서 후퇴한 지점과 그 이유를 본문에 명시한다. 후퇴는 리뷰에서 논증된 것이며, 이 RFC의 스코프가 최종 합의안이다.

### 1.2 현재 main 기준으로 유효한 구조 문제 (본 RFC의 대상)

1. **Markdown-as-database**: 캡슐 canonical 상태가 `TASK.md` 테이블 그 자체. 파싱은 `src/services/markdown-table.ts`의 라인 기반 문자열 처리, 검증은 `src/harness/validate.ts`의 ~16개 토큰셋 + `src/services/docs-registry.ts`의 7개 vocab — 공유 소스 없음. `/compact` 후 캡슐 마크다운 정합성 붕괴(known_issue #1)는 이 구조의 필연.
2. **다중 문서 동기화**: 같은 사실("M3 완료")이 TASK.md/TASK_BOARD/PROJECT_STATE/AGENT_HANDOFF/DEVELOPMENT_SLICES 5곳에 존재, 자동 갱신은 TASK_BOARD 1곳뿐. known_issue #9(수동 폴더 삭제 후 넘버링 드리프트)는 마크다운과 숨은 상태의 이중화가 이미 드리프트를 만들고 있다는 자체 증언.
3. **사후 토큰 검증**: 허용 토큰을 finalize 실패로 배우는 구조 (FD-009).
4. **의례 고정비가 캡슐 크기를 왜곡**: known_issue #6("캡슐이 너무 작고 토큰 낭비")과 동일 방향.

## 2. 설계 원칙 (리뷰 반영판)

1. **구조화 가능한 것만 canonical store로.** 사람의 판단·요약·맥락 산문은 사람 소유 문서에 남는다.
2. **Write-time validation.** 잘못된 입력은 저장 시점에 허용값 목록과 함께 거부. finalize에서 처음 알게 되는 검증 0건.
3. **의례는 위험에 비례하되, close 안전성은 스냅샷 해시가 담당한다.** rev는 store 내부 동시성 제어일 뿐이다 (§5).
4. **캡슐 지역성(capsule locality) 불변.** `tasks/T-*/`는 evidence를 포함한 self-contained 감사 단위로 유지 (§4).
5. **작게 검증하고 증거로 확장한다.** 첫 canonical store는 DEVELOPMENT_SLICES 하나. 확장은 측정된 증거(§9)로 결정.

## 3. Projection 스코프: 3계층 소유권 모델

원안의 "전 문서 generated"를 철회하고, 문서를 세 계층으로 나눈다.

### Tier 1 — 완전 생성 문서 (full projection)

**후보: `docs/TASK_BOARD.md`, `docs/DEVELOPMENT_SLICES.md`, `tasks/T-*/EVIDENCE.md`(현행 유지)**

- canonical은 state store, 파일은 100% 재생성 가능
- 파일 머리에 `<!-- generated by hadara render; edit via hadara CLI -->` 1줄
- 갱신에 의례 없음 — 단, 아래 **소유권 계약**이 성립할 때만:

> **소유권 계약 (무의례 갱신의 성립 조건)**
> 1. 블록/문서가 **완전한** projection이다 (canonical에 없는 정보가 파일에 없다)
> 2. canonical state에서 **언제든 재생성 가능**하다
> 3. 사람/에이전트가 해당 파일(블록)을 **직접 편집하지 않는다**는 계약이 있다
>
> 이 계약이 없으면 무의례 갱신은 handoff.update 사건을 블록 단위로 재생산한다
> (CLI가 사람의 편집을 조용히 덮어쓰는 것 — 그 사건의 본질).
> 계약 위반(직접 편집)은 `hadara doctor`가 렌더 해시 불일치로 감지하고,
> **조용한 덮어쓰기 대신** "state로 import 또는 재렌더로 discard" 선택을 강제한다.

### Tier 2 — 사람 소유 문서 + 생성 블록 (hybrid)

**후보: `docs/PROJECT_STATE.md`(상태 표만 생성 블록), `docs/AGENT_HANDOFF.md`(validation baseline, last-completed 표만 생성 블록)**

- 문서 전체의 소유자는 사람/에이전트. 판단·요약·"Next Recommended Step"의 근거 산문은 자유 작성
- 구조 데이터 표만 생성 블록으로 삽입 — 단방향 sync (state → 블록), 블록에는 Tier 1과 동일한 소유권 계약과 드리프트 감지 적용
- **의례 없음의 근거는 Tier 1과 동일한 계약**이지, 블록이라는 형태가 아니다
- 전면 generated로 만들지 않는 이유(리뷰 합의): 이 문서들의 가치는 사람의 운영 감각 — 요약, 우선순위 판단, 경고의 뉘앙스 — 이고 그것은 state로 환원되지 않는다

**생성 블록 마커 예시** (구현 기준):

```markdown
## Validation Baseline

<!-- hadara:generated:start validation-baseline {"schema":"hadara.generatedBlock.v1","source":"state/tasks","renderer":"render.validation-baseline"} -->
| Check | Latest Evidence | Notes |
|---|---|---|
| Focused tests | ev:T-0512:... | Passed. |
<!-- hadara:generated:end validation-baseline -->

위 표에 대한 운영 판단이나 경고 산문은 마커 밖, 이 위치처럼 자유롭게 쓴다.
```

- 마커 **안**은 CLI 소유: 사람/에이전트 직접 편집 금지 계약. 렌더러가 state에서 통째로 재생성
- 마커 **밖**은 사람 소유: CLI는 어떤 경우에도 마커 밖 텍스트를 건드리지 않는다
- `hadara doctor`는 블록 본문 해시를 state 렌더 결과와 대조해 계약 위반(마커 내부 직접 편집)을 드리프트로 감지하고, 이후 렌더는 조용히 덮어쓰는 대신 "state로 import 또는 재렌더로 discard"를 요구한다
- 기존 `hadara:managed:*` 마커와 문법이 유사하나 의미가 다르다: managed section은 양방향 편집 가능 영역을 before-hash로 보호하는 것(Tier 3으로 존속), generated block은 단방향 projection이며 편집 자체가 계약 위반이다. 마커 이름을 다르게 가져가는 이유가 이 의미 구분이다

### Tier 3 — 혼합 섹션 패치 (기존 메커니즘 존속)

- 사람 산문과 CLI 갱신이 **같은 섹션 안에서** 섞여야 하는 예외 케이스
- 현행 `docs.patch`의 before-hash 보호를 **그대로 유지** — 여기서는 의례가 정당하다 (섹션 상태를 CLI가 재생성할 수 없으므로 스냅샷 검증 외에 보호 수단이 없음)
- 목표는 Tier 3을 최소화하는 것이지 0으로 만드는 것이 아님

### TASK.md의 위치

TASK.md는 장기적으로 Tier 2다: Goal notes/Scope 산문/Change summary 산문은 작성 소유, Plan/Acceptance/Validation/Risks의 **구조 열**은 state 기반 생성 블록. 단 이 전환은 slice 프로토타입(§9) 검증 후의 두 번째 확장 후보이며 본 RFC 채택 시에도 즉시 착수하지 않는다.

## 4. Evidence: task-local canonical 유지 (원안 철회)

proposal.md의 `.hadara/evidence/T-*.jsonl` 중앙화를 **철회**한다.

- `tasks/T-*/evidence.jsonl`이 canonical로 존속. 캡슐 디렉터리가 evidence를 포함한 self-contained 감사 단위라는 성질(HADARA의 차별적 강점)을 보존한다
- 중앙 store(`.hadara/state/`)는 evidence에 대해 **index/cache/projection까지만** 가진다 — 검색·집계·brief 렌더용 파생 데이터이며, 삭제해도 재구축 가능해야 한다
- 캡슐 이동/아카이브 시 evidence가 함께 움직인다는 현행 성질이 불변임을 테스트로 고정한다

`docs-registry.json`도 현 위치(`.hadara/docs-registry.json`) 유지. 원안의 위치 재배치는 이득 대비 마이그레이션 비용이 정당화되지 않는다.

## 5. 동시성과 close 안전성: 두 도메인의 분리 (rev CAS 주장 철회)

proposal.md의 "rev CAS가 planHash를 대체한다"는 주장을 **철회**한다. 리뷰 지적대로 현행 close proof는 close-source 문서 해시, validation report 해시, slot registry 해시를 묶어 "close 판단이 근거한 세계"를 스냅샷하며, state store의 단조 rev는 이 세계를 대표하지 못한다 (task-local evidence append, 사람의 문서 편집, close-source 파일 변경은 rev를 올리지 않는다).

### 5.1 Domain A — state store 내부 (rev의 역할)

- aggregate 단위 rev (slices.json, 향후 task state 파일 각각)
- **rev를 올리는 write set**: `hadara slice/task set/...` 등 state API를 통과하는 모든 쓰기. 그 외에는 없음 (파일 직접 편집은 doctor 드리프트 감지의 영역이지 rev의 영역이 아님)
- 용도: 동시 CLI/에이전트 프로세스 간 lost-update 방지 (compare-and-swap). **close 안전성과 무관**

### 5.2 Domain B — close-source 세계 (스냅샷 해시의 역할, 현행 유지)

- close 시점 스냅샷 = close-source 문서 content hash + validation report hash + slot registry hash + task-local `evidence.jsonl` tail 위치
- state store가 도입되어도 이 스냅샷 집합은 **축소되지 않는다.** state 파일이 close-source가 되면 스냅샷에 **추가**된다 (rev가 아니라 content hash로)

### 5.3 저의례 close의 형태

왕복을 줄이는 방법은 해시를 없애는 것이 아니라 **왕복을 커맨드 내부로 접는 것**이다:

```
hadara task finalize --execute --auto   (0.4.1, FD-010)
# 내부: Domain B 스냅샷 채취 → finish/ready/close/audit 검사
#   → 전부 clean이면 쓰기 직전 스냅샷 재검증 → 일치 시 commit (1회 호출 종료)
#   → 블로커 발견 시 아무것도 쓰지 않고 dry-run과 동일한 보고
#   → 재검증 불일치 시 중단 (현행 planHash mismatch와 동등한 보호)
```

안전성 약화 없이 왕복만 제거된다. 0.5의 `task close`는 이 `--auto` 경로가 기본값이 된 표면이다.

## 6. 장기 방향으로 유지하는 기능 (0.5 본체)

리뷰에서 독립적 가치를 인정받은 항목. 각각 slice 프로토타입 검증 후 별도 캡슐로:

| 기능 | 요지 | 선행 조건 |
|---|---|---|
| `hadara brief` | 세션 시작 단일 진입점: 프로젝트 큰 그림 + slice 지도 + 활성 캡슐 + carry-forward 경고 + next actions를 JSON 1회 호출로. known_issue #3/#12(새 세션의 큰그림 유실)의 직접 해법 | slices state (rc0 프로토타입) |
| `verify --ac` | `validation run` 계승 + AC 자동 연결: 실행→분류→evidence 기록까지 현행 유지, `acceptance[AC-n].state`와 evidence 연결을 자동화. "모든 gate AC met"이 기계 판정 가능해져 §5.3의 clean-path 판정 근거가 됨 | task 구조 필드의 state화 |
| vocab 단일 소스 | `harness/validate.ts` ~16 토큰셋 + `docs-registry.ts` 7 vocab을 단일 vocab 정의로 통합, MCP tool schema도 여기서 생성. **조회 surface는 0.4.1에서 선행**(rc0-scope 항목 2), 통합은 0.5 | 없음 (0.4.1과 분담) |
| slice 일급 객체 | 마일스톤/백로그를 state 객체로: `slice add/set`, `task create --slice`, 의존성 기반 next-work 추천 | rc0 프로토타입이 곧 이것의 1단계 |

### 6.1 스코프에서 제외하고 별도 RFC로 분리하는 것

- **커맨드 포트폴리오 (90→N 축소)**: 표면 위생과 기능 제거가 섞인 문제로, 사용 계측 없이 결정 불가. 별도 command-portfolio RFC로
- **context pack/slice 폐기**: **철회.** privacy boundary, bounded slicing, task-scoped routing은 단순 파일 읽기와 다른 가치다. 실측된 문제는 기능 가치가 아니라 디스커버리(실사용 세션에서 자발적 호출 0회)이므로, 방향은 "폐기"가 아니라 "`brief`의 pointers로 진입점 통합 + 호출 계측 후 standalone 표면 재평가"

## 8. 마이그레이션 원칙

1. **임포터는 기존 파서다**: `markdown-table.ts` + `harness/validate.ts`가 기존 문서 → state 임포트를 담당. 신규 파서 작성 없음
2. 렌더 출력은 기존 문서 구조와 최대 동형 (사람 독자의 연속성, git diff 리뷰 가능성)
3. 단계별 opt-in: slice(rc0) → project 상태 표 → task 구조 필드. 각 단계는 이전 단계의 §9 지표 충족이 조건
4. 산문은 무손실: 구조화 실패 내용은 note/text 필드로 수용하되, **산문의 1차 저장소는 어디까지나 사람 소유 문서다** (state에 산문을 넣어 다시 렌더하는 것은 작성 표면만 옮기는 것이므로 하지 않는다)

## 9. 채택 게이트: 0.4.1 프로토타입의 성공 지표

본 RFC의 확장(project.json, task state, Tier 2 블록)은 `docs/specs/0.4.1/rc0-scope.md` 항목 5(DEVELOPMENT_SLICES 한정 state/render)가 다음을 **측정 가능하게** 통과했을 때만 진행한다:

| 지표 | 통과 기준 |
|---|---|
| diff 노이즈 | slice 상태 1회 변경이 만드는 git diff가 (state 파일 + 렌더 파일) 리뷰 가능한 크기이고, 무변경 재렌더는 diff 0 |
| 마이그레이션 비용 | 기존 DEVELOPMENT_SLICES.md → import → render 왕복이 무손실이며, 임포트 실패 케이스가 보고서로 전량 표면화 |
| close-proof 안정성 | slices.json이 close-source에 추가된 뒤에도 기존 캡슐들의 finalize/audit-close가 회귀 없이 통과 |
| 소유권 계약 작동 | 렌더 파일 직접 편집 시 doctor가 드리프트를 감지하고 조용한 덮어쓰기가 발생하지 않음 (테스트로 고정) |
| 운영 만족 | 도그푸딩 캡슐 N개에서 slice 관련 수동 문서 동기화가 실제로 0회가 됨 |

하나라도 실패하면: 실패 지표를 evidence로 남기고 본 RFC를 개정하거나 기각한다.
