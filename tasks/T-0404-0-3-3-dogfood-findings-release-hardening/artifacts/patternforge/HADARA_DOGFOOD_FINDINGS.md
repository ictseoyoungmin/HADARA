# HADARA Dogfood Findings

This file records HADARA 0.3.3 findings discovered while building PatternForge.

## Finding Table

| ID | Capsule | Surface | Severity | Finding | Proposed Action | Release Impact | Status |
|---|---|---|---|---|---|---|---|
| PF-F-001 | PF-001 | `init --help` | Medium | Running `hadara init --help` initialized the current project instead of showing help. In HADARA-dev the worktree stayed clean, but the behavior is surprising and risky for users expecting a read-only help command. | Add command-family help handling for `init --help`, or route unknown help invocations to `help command init` without mutation. | Consider before stable 0.3.3 if easy; otherwise rc1/nice-to-have. | Open |
| PF-F-002 | PF-001 | `session start` | Low | Bounded `session start --json` suggests `node dist/cli/main.js ...` commands even when the active binary is installed from npm at `/tmp/patternforge-dogfood-tools/node_modules/.bin/hadara`. | Prefer `hadara ...` in generated guidance for installed projects, or include the observed CLI entry path from runtime metadata. | Not a blocker; command args are present and correct. | Open |
| PF-F-003 | PF-001 | `context graph` | Low | Fresh installed-package project reports missing source-checkout files such as `src/services/capability-registry.ts` and `docs/RELEASE_READINESS.md`. The warning is technically true but source-checkout oriented and noisy for product repos. | Down-rank source-checkout-only context graph warnings for initialized consumer projects, or explain they are optional source-addressed metadata. | Not a blocker; graph still routes task/docs. | Open |
| PF-F-004 | PF-001 | `init register-doc` / `docs explain` | Medium | `init register-doc --execute` added SOP Required Reading rows but `docs explain` still reported the new docs as `DOC_NOT_REGISTERED` until `.hadara/docs-registry.json` was updated separately. | Make register-doc update both the SOP required-reading table and machine-readable docs registry, or document the split clearly and provide one command to update both. | Consider before stable 0.3.3 because it affects context-routing trust in fresh projects. | Open |
| PF-F-005 | PF-002 | `context pack` | Low | PF-002 is explicitly a product requirements task, but task-scoped context pack did not surface `docs/PATTERNFORGE_DOGFOOD_PLAN.md` until the task docs referenced it. | Add registry/title/keyword relevance for project-specific docs, or encourage task create templates to seed relevant spec links. | Follow-up; manual read was sufficient. | Open |
| PF-F-006 | PF-003 | `init register-doc` | Medium | Registering `docs/COMPOSE_PLATFORM.md` repeated PF-F-004: SOP Required Reading was updated, but machine-readable docs registry still needed a separate update before `docs explain` could see the document. | Same as PF-F-004; register-doc should update every registry source it expects readers/context routing to trust. | Consider before stable 0.3.3. | Open |
| PF-F-007 | PF-003 | `evidence add-command --help` | Medium | Running `hadara evidence add-command --task T-0003 --help --project ...` appended an `unknown` evidence record instead of showing help. This is the same write-command help mutation class as PF-F-001, but on a proof-producing command. | Ensure `--help` is globally read-only before command execution, especially for write/evidence commands. Consider linting unknown evidence generated from help-like invocations. | Consider before stable 0.3.3 because accidental proof noise is costly in governed projects. | Open |
| PF-F-008 | PF-006 | Docker compose build loop | Low | PF-006 compose build used cached layers but still spent noticeable time in Docker registry metadata/provenance resolution. This slows iterative dogfood capsules more than application code changes require. | Document a fast dev-loop compose mode or evaluate build flags/cache guidance during performance audit capsules. | Follow-up; not a stable 0.3.3 blocker. | Open |
| PF-F-009 | PF-010 | `context pack` validation hints | Low | `hadara context pack --task T-0010` routed the current task and state docs correctly, but `validateWith` still suggested `node dist/cli/main.js ...` and a HADARA-dev unit test path inside an installed consumer project. | Context pack should prefer the active installed `hadara` command and avoid source-repo test hints when the project has no HADARA-dev checkout. | Follow-up; it is noisy but did not block work. | Open |
| PF-F-010 | PF-016 | `task status` after finalize | Medium | In the throwaway installed-package project, `task finalize --execute` produced `closed-valid`, but a later `task status` still emitted a required handoff update next action. This can encourage editing close-source docs after close, conflicting with the 0.3.3 finalize-first lifecycle guidance. | After `closed-valid`, downgrade handoff refresh to advisory unless close-source docs are invalid, or make finalize require/verify handoff freshness before close. | Consider before stable 0.3.3 because it affects agent lifecycle behavior. | Open |
| PF-F-011 | PF-016 | Acceptance authoring | Low | A task acceptance row that requires `closed-valid` blocks done-level readiness because close evidence cannot exist before readiness. | Add lifecycle template guidance: acceptance should require close-ready dry-run before close; final `closed-valid` belongs in status/evidence after finalize. | Follow-up; guidance issue, not runtime blocker. | Open |
| PF-F-012 | PF-017 | `context pack` state projection | Medium | `context pack --task T-0017` reported `STATE_TASK_BOARD_MISSING_ROW` for every Task Capsule even though `docs/TASK_BOARD.md` contains the rows and `task status` resolves individual task board status correctly. | Investigate state projection's Task Board extraction path against the current generated board format and cache refresh behavior. | Consider before stable 0.3.3 because it can undermine context-routing trust. | Open |
| PF-F-013 | PF-017 | `context graph --task` output size | Low | `context graph --task T-0017 --json` emitted an extremely large graph in a realistic project, causing shell output truncation. The command is correct but awkward as an agent-facing task-scoped diagnostic. | Add a compact summary mode, default bounded task graph output, or explicit `--full` for large graphs. | Follow-up; usability issue, not a correctness blocker. | Open |
| PF-F-014 | PF-018 | `task finalize` dry-run remediation visibility | Low | `task finalize --task T-0018 --json` initially reported only the next executable finish step, while `task status` gave the full blocker inventory. This is logical for execution planning but less useful when an agent wants all remediation work before editing docs. | Add an optional remediation summary to finalize dry-run, or document that agents should pair `task lifecycle` with `task status` before final close preparation. | Follow-up; lifecycle remains correct. | Open |
| PF-F-015 | PF-019 | Evidence id propagation | Low | After evidence append, the same durable evidence id must be copied into multiple close-source docs by hand. This is transparent but repetitive and creates opportunities for documentation drift. | Add a helper that summarizes latest substantive evidence id and optionally patches standard Task Capsule evidence cells before finish, or provide generated evidence reference blocks. | Follow-up; productivity improvement. | Open |

## Release Impact Classes

| Class | Meaning |
|---|---|
| Blocker | Stable 0.3.3 should not publish before this is fixed. |
| Consider | Worth fixing before stable if small and low-risk. |
| Follow-up | Product-dogfood friction that can move to 0.3.4 or later. |
